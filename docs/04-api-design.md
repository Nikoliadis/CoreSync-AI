# 04 · API Design

REST over HTTPS, JSON, OpenAPI 3.1 generated by FastAPI. Base URL `https://api.coresync.ai/v1`.

---

## 1. Conventions

### 1.1 Resource naming
- Plural nouns, kebab-free: `/workouts/sessions`, `/nutrition/diary`.
- Nesting only where the child cannot exist without the parent:
  `/workouts/sessions/{id}/exercises/{id}/sets`.
- Actions that are not CRUD get a verb sub-resource: `POST /workouts/sessions/{id}/complete`.
  This beats overloading `PATCH` with a `status` field — the operation has its own
  authorisation, validation and side effects, so it deserves its own endpoint.

### 1.2 Methods & status codes

| Method | Use | Success |
|---|---|---|
| `GET` | Read. Always safe, always cacheable | 200 |
| `POST` | Create, or an action | 201 (+ `Location`) / 200 / 202 for async |
| `PATCH` | Partial update (the default for updates) | 200 |
| `PUT` | Full replace — used only for singleton sub-resources like `/me/settings` | 200 |
| `DELETE` | Soft delete for user content, hard for tokens | 204 |

Errors: `400` validation shape, `401` unauthenticated, `403` authenticated but not permitted,
`404` absent **or not visible to you**, `409` conflict/state violation, `410` gone,
`413` payload too large, `422` semantically invalid, `429` rate limited, `402` quota/tier,
`5xx` ours.

> `404` rather than `403` for another user's resources — a `403` confirms the resource exists,
> which is an enumeration oracle.

### 1.3 Request headers

| Header | Required | Purpose |
|---|---|---|
| `Authorization: Bearer <jwt>` | authenticated routes | Access token |
| `X-Request-Id` | optional | Client-supplied trace id; echoed in the response and every log line |
| `Idempotency-Key` | POST that creates | UUID; result cached 24 h in Redis (see §6) |
| `X-Client-Version` | yes | `ios/1.4.2`, `web/2026.7.1`. Drives minimum-version enforcement |
| `X-Timezone` | yes on write | IANA name; used to compute `local_date` server-side |
| `Accept-Language` | optional | Localised validation messages and AI responses |

### 1.4 Response envelope

Single resource — the object itself, unwrapped:

```json
{ "id": "0192f8e0-...", "name": "Push Day A", "createdAt": "2026-07-28T18:42:11Z" }
```

Collection — data plus pagination metadata:

```json
{
  "data": [ { "id": "..." } ],
  "pagination": {
    "nextCursor": "eyJpZCI6IjAxOTJm...",
    "previousCursor": null,
    "hasMore": true,
    "limit": 50
  }
}
```

**camelCase on the wire, snake_case in Python.** Pydantic aliases handle the translation in one
place, so neither side writes unnatural code.

### 1.5 Error contract

One shape for every error, machine-readable first:

```json
{
  "error": {
    "code": "validation_error",
    "message": "The request could not be validated.",
    "requestId": "01H8X...",
    "details": [
      { "field": "sets[0].weightKg", "code": "less_than_equal", "message": "must be ≤ 1000" }
    ]
  }
}
```

Clients branch on `code`, never on `message`. The full code registry lives in
`backend/src/coresync/core/errors.py` and is published in the OpenAPI spec.

| Code | HTTP | Meaning |
|---|---|---|
| `validation_error` | 400 | Malformed or invalid input |
| `unauthenticated` | 401 | Missing/expired access token |
| `token_reuse_detected` | 401 | Rotated refresh token replayed — all sessions revoked |
| `email_not_verified` | 403 | Action requires a verified email |
| `forbidden` | 403 | Authenticated, not permitted |
| `not_found` | 404 | Absent or not visible |
| `conflict` | 409 | e.g. a workout is already in progress |
| `quota_exceeded` | 402 | AI/tier limit reached; body includes `upgradeUrl` |
| `rate_limited` | 429 | Includes `Retry-After` |
| `upstream_unavailable` | 503 | LLM/food provider down; body says whether to retry |

### 1.6 Pagination

**Cursor-based everywhere.** Offset pagination degrades linearly and skips or duplicates rows
when data is inserted mid-scroll — unacceptable for an infinite-scrolling history.

```
GET /v1/workouts/sessions?limit=50&cursor=eyJkIjoiMjAyNi0wNy0wMSIsImkiOiIwMTkyLi4uIn0
```

The cursor is a base64 JSON tuple of the sort keys (`local_date`, `id`), signed to prevent
tampering. `limit` defaults to 25, caps at 100.

Exception: admin tables use offset pagination with a total count, because page numbers are the
expected UX there and the row counts are small.

### 1.7 Filtering, sorting, sparse fields

```
GET /v1/exercises?muscleGroup=chest&equipment=dumbbell&difficulty=beginner&q=press&sort=-popularity
GET /v1/workouts/sessions?from=2026-01-01&to=2026-06-30&fields=id,name,localDate,totalVolumeKg
```

- Filters are explicit, typed query parameters — never a generic `filter[...]` DSL, which is
  impossible to validate, cache or index for.
- `sort` accepts an allow-list of fields only; `-` prefix for descending.
- `fields` trims the response for bandwidth-sensitive mobile lists.

### 1.8 Versioning
URL-versioned (`/v1`). A new major version is cut only for breaking changes; additive changes
ship in place. Two majors are supported concurrently for at least 12 months, because mobile
clients cannot be force-upgraded quickly. `Sunset` and `Deprecation` headers announce retirement.

## 3. Rate limiting

Sliding-window counters in Redis, keyed by user id (or IP when anonymous). Every response
carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.

| Bucket | Limit | Reason |
|---|---|---|
| Anonymous, per IP | 30 / min | Registration and login abuse |
| `POST /auth/login` per IP+email | 5 / 15 min | Credential stuffing |
| `POST /auth/password/forgot` per email | 3 / hour | Email bombing |
| Authenticated, global | 120 / min | General fairness |
| `POST .../sets` | 300 / min | Deliberately generous — never throttle a lifter mid-workout |
| `POST /workouts/sessions/sync` | 20 / min | Bulk endpoint, big payloads |
| `GET /nutrition/foods/search` | 60 / min | Typeahead; debounced client-side to 300 ms |
| `POST /ai/.../messages` | 60 / hour + token budget | Cost control |
| Uploads | 50 / day | Storage abuse |

Rate limiting runs at two layers: Front Door / WAF for volumetric attacks, and application
middleware for per-user fairness. The application layer is authoritative for anything that
depends on user identity or tier.

## 4. Caching

| Resource | Strategy | TTL |
|---|---|---|
| `/exercises` catalog | `ETag` + `Cache-Control: private, max-age=3600`, Redis behind it | 1 h / invalidated on publish |
| `/exercises/meta/*` | `public, max-age=86400` | 24 h |
| `/nutrition/foods/{id}` | Redis, keyed by id + version | 24 h |
| Food search results | Redis, keyed by normalised query | 10 min |
| `/users/me` | No HTTP cache; Redis behind it, invalidated on write | 5 min |
| Dashboard `/progress/stats/overview` | Redis per user+date | 5 min |
| AI context bundle | Redis per user | 15 min |
| Signed media URLs | Never cached | 15 min TTL on the URL itself |

Invalidation is **event-driven, not TTL-hopeful**: the service that writes a workout deletes
`user:{id}:summary:*` in the same unit of work.

## 5. Concurrency & consistency

- **Optimistic locking** on routines and custom foods via a `version` integer; a stale `PATCH`
  gets `409` with the current state so the client can merge.
- **`If-Match` / `ETag`** supported on singleton resources (`/me/settings`).
- **Advisory locks** (Redis + Postgres) around session completion, so a double-tapped "Finish"
  cannot compute PRs twice.
- **Read-after-write:** endpoints that a client reads immediately after writing are always
  served from the primary, never the replica.

## 6. Idempotency

Any `POST` that creates a resource accepts `Idempotency-Key`.

```
POST /v1/workouts/sessions/{id}/complete
Idempotency-Key: 0192f8e0-7b3a-7c4d-9e2f-1a2b3c4d5e6f
```

Implementation: `SETNX idem:{userId}:{key}` with a 24-hour TTL and the serialised response. A
replay returns the stored response with `Idempotency-Replayed: true`. In-flight duplicates get
`409 request_in_progress` rather than a second execution.

This is not optional polish — a phone on gym Wi-Fi retries constantly, and a duplicated workout
session or a double-logged meal is a visible data-corruption bug.

## 7. Offline sync contract

The mobile app keeps a local write-ahead log and flushes it here.

```http
POST /v1/workouts/sessions/sync
Content-Type: application/json

{
  "deviceId": "0192...",
  "operations": [
    { "opId": "0192...a1", "type": "session.create",
      "at": "2026-07-28T17:02:00Z", "payload": { "id": "0192...s1", "routineId": "...", "startedAt": "..." } },
    { "opId": "0192...a2", "type": "set.log",
      "at": "2026-07-28T17:06:12Z", "payload": { "id": "0192...x1", "sessionExerciseId": "...", "reps": 8, "weightKg": 100 } },
    { "opId": "0192...a3", "type": "session.complete",
      "at": "2026-07-28T18:01:44Z", "payload": { "id": "0192...s1" } }
  ]
}
```

```json
{
  "results": [
    { "opId": "0192...a1", "status": "applied" },
    { "opId": "0192...a2", "status": "duplicate" },
    { "opId": "0192...a3", "status": "applied",
      "result": { "newPersonalRecords": [ { "exerciseId": "...", "recordType": "est_1rm", "value": 126.7 } ] } }
  ],
  "serverTime": "2026-07-28T18:02:03Z"
}
```

Rules that make this safe:

1. **Client-generated UUIDv7 ids.** The client names the entity; the server accepts the name.
2. **`opId` is the idempotency unit.** Replaying the whole batch is always safe.
3. **Operations apply in client order** within one transaction per session.
4. **Partial success is expressible.** One bad operation does not reject the batch; it returns
   `rejected` with a reason and the client surfaces it.
5. **Conflicts resolve last-write-wins per field**, using the client's `at` timestamp bounded by
   server time — a phone with a wrong clock cannot win by claiming to be from 2030.
6. **Deletes are tombstones**, so a delete that syncs after a stale edit still wins.

## 8. OpenAPI & client generation

FastAPI generates the spec from Pydantic models; every endpoint declares its `response_model`,
its error responses and an example. CI then:

1. Generates `openapi.json`.
2. Runs **Schemathesis** property-based tests against the spec (fuzzes every endpoint for
   contract violations and unhandled 500s).
3. Generates TypeScript types into `frontend/src/lib/api-types` via `openapi-typescript`.
4. Fails the build if the diff against the previous release contains a **breaking** change
   without a version bump (`oasdiff` in breaking-change mode).

Web and mobile therefore never hand-write a request type, and a backend rename that would break
a client fails CI instead of production.
